# 營運手冊

上線後怎麼管理這個服務。假設由一到兩個人兼職營運。

## 你的工具

| 工具 | 用途 |
| --- | --- |
| 營運後台 `/admin` | 月經常性收入、店家數、付費轉換率、每間店的用量、收款紀錄、資料庫大小與備份、操作稽核 |
| 主機平台（Fly 或 VPS） | 部署、回滾、看日誌（`fly logs` 或 `docker compose logs -f app`） |
| 綠界廠商後台 | 對帳、退款、查扣款失敗原因、開發票 |
| Resend 後台 | 信件送達率、退信 |
| 外部監控 | 每分鐘打 `/api/health`，掛掉時通知 |

## 例行工作

**每天**
- 不需要固定進後台。有異常時系統會寄信到 `ADMIN_EMAILS`，信裡會寫該做什麼。
- 回覆客服信件（店家回覆系統信會寄到 `SUPPORT_EMAIL`）。

**每週**
- 看週一寄來的週報。裡面列出開店三天還沒收到預約的店家；系統已經自動寄過引導信，親自聯繫的效果更好。
- 聯繫扣款失敗的店家。系統在到期後保留 3 天付費功能，這段時間聯繫最有效。

**每月**
- 綠界後台對帳：實收金額對營運後台的「近 30 天實收」。
- 到 GitHub Actions 確認每日異地備份有成功。
- 套用安全更新：`npm audit`、`npm update`，跑 `npm run check` 與 `npm run e2e` 後部署。

**每季**
- 演練一次還原備份。
- 檢視定價與各方案的轉換率。

## 系統自動做的事

伺服器每 10 分鐘執行一次（`src/lib/jobs.ts`），每項都可重複執行、互不影響：

| 工作 | 內容 |
| --- | --- |
| 預約提醒 | 有留 Email 的客人，在預約前一天早上 9 點後收到提醒信（所有方案） |
| 明日預約摘要 | 每晚寄給店家隔天的預約清單，並標出沒留 Email、需要自己提醒的客人。當天沒有預約就不寄 |
| 信箱驗證提醒 | 店家收到第一筆預約但信箱還沒驗證時，再寄一次驗證信（一天最多一次） |
| 訂閱到期 | 綠界訂閱超過到期日 3 天仍未續扣、或已取消且到期者，降回免費版並寄信通知 |
| 終止訂閱重試 | 換方案留下的舊訂閱、到期未續的訂閱，向綠界終止扣款；失敗就下次再試。卡住的會顯示在營運後台最上方 |
| 清理 | 刪除過期的登入、重設密碼連結、30 天前的寄信紀錄、一年前的稽核紀錄 |
| 備份 | 每天一份資料庫快照，保留 7 份 |
| 新店家引導信 | 開店後第 1、3、7 天仍沒有線上預約的店家，各寄一封具體的下一步。店家可在設定關閉 |
| 異常通知 | 寄信失敗、扣款失敗、訂閱終止卡住、備份超過兩天沒成功時，寄信到 `ADMIN_EMAILS`。同樣的狀況一天只寄一次 |
| 週報 | 每週一早上寄出：月經常性收入、店家數、上週預約量，以及值得主動聯繫的店家名單 |

## 備份與還原

- **本機快照**：自動，存在資料磁碟的 `backups/`。營運後台可看到份數與最新日期，也可手動觸發。
- **異地備份（自動）**：`.github/workflows/backup.yml` 每天凌晨從正式站拉一份快照，加密後存成 GitHub Artifact，保留 30 天。只要在 repo 的 Secrets 設好 `APP_URL`、`BACKUP_SECRET`、`BACKUP_PASSPHRASE` 就會開始運作。密語請另外保管，遺失就無法解密。
- **手動下載**：營運後台的「下載最新備份」。檔案含全部店家與顧客資料，請放在加密磁碟。
- **還原**：步驟在 `deploy/restore.md`。

## 儲存空間

實測每筆預約連同索引約佔 0.5 KB。

| 規模 | 每月新增預約 | 一年資料量 |
| --- | --- | --- |
| 100 間店 | 約 2 萬筆 | 約 120 MB |
| 1,000 間店 | 約 20 萬筆 | 約 1.2 GB |

1 GB 磁碟可撐到數百間店；磁碟用量超過 60% 時擴充（Fly：`fly volumes extend`，不需停機）。7 份備份會讓磁碟用量約為資料庫的 8 倍，資料庫超過 500 MB 後把 `BACKUP_KEEP` 降到 3 並依賴異地備份。

## 流量管控

三層防護，由外到內：

1. **Cloudflare**：DDoS 防護、CDN 快取靜態檔。
2. **進入點限流**（`src/proxy.ts`）：每個 IP 每分鐘最多 120 次公開 API 呼叫，超過回 429。金流回呼不受限。
3. **動作限流**：登入每個「IP＋帳號」10 分鐘 8 次；註冊每 IP 每小時 8 次；每間店每 IP 每小時 10 筆預約；忘記密碼每 Email 每小時 3 次。

商業面的管控是免費版的每月 30 筆線上預約額度：超過後仍會收單，但店家要升級才看得到客人的聯絡方式。灌單由上面的限流與蜜罐欄位擋下。

如果某間店被惡意灌預約：在營運後台對該店按「停權」可立即暫停其線上預約（店家後台仍可使用），處理完再解除。

## 客服常見情況

| 情況 | 處理 |
| --- | --- |
| 店家手機遺失、兩步驟驗證進不去 | 先請他用備用碼。備用碼也沒有時，確認身分後在資料庫把該帳號的 `totp_enabled` 設為 0 |
| 店家忘記密碼 | 請他用登入頁的「忘記密碼」。收不到信時到 Resend 後台查是否退信 |
| 營運後台出現「定期定額還沒成功終止」 | 系統會自動重試。超過一天還在，到綠界廠商後台手動停用該筆，並確認店家沒有被多扣；有的話退款 |
| 稽核紀錄出現 `orphan-charge` | 有訂閱在店家沒有方案時扣了款。到綠界後台退款給該筆交易 |
| 店家說付了錢但沒升級 | 綠界後台查該筆交易是否成功 → 營運後台看是否有收款紀錄。有交易沒紀錄代表回呼沒進來，確認 `APP_URL` 正確後，用「手動方案」先幫他開通並註明原因 |
| 要退款 | 在綠界後台退刷，再請店家於帳單頁取消訂閱 |
| 銀行轉帳的客戶、合作夥伴、補償 | 營運後台「手動方案」，原因會留在稽核紀錄 |
| 客人想改時間 | 客人可從自己的預約連結按「改時間」；店家也能在後台改期 |
| 客人要求刪除個資 | 請他聯繫預約的店家；店家在「顧客」頁可刪除該顧客的個人資料 |
| 店家要求刪除帳號 | 店家自己在「店家設定」最下方操作；需先取消訂閱 |
| 店家要改預約頁代稱 | 目前不開放（避免已分享的連結失效）。必要時直接改資料庫的 `businesses.slug` |
| 違規店家 | 營運後台停權，並依服務條款通知 |

## 故障處理

1. **網站打不開**：`fly status` 或 `docker compose ps` 看容器是否在跑；看日誌；必要時回滾上一版。
2. **資料異常**：先手動備份現況（營運後台「立即備份」或直接複製檔案），再調查。不要在沒有備份的情況下動資料庫。
3. **寄信失敗**：營運後台會顯示失敗數。常見原因是 Resend 額度用完或網域驗證失效。預約本身不受影響。
4. **綠界回呼失敗**：付款成功但方案沒變。回呼處理是冪等的，修好後可在綠界後台重送通知，或用手動方案補開。
5. 事後記錄：發生了什麼、影響多少店家、怎麼避免再發生。

## 擴充時機

| 訊號 | 該做的事 |
| --- | --- |
| 記憶體長期超過 80% | 升到 1 GB 機器 |
| 預約頁 95 百分位延遲超過 1 秒 | 升級 CPU；檢查是否有慢查詢 |
| 付費店家超過約 1,000 間，或需要不停機部署 | 資料庫換成 Postgres、限流換成 Redis、應用程式開兩台。查詢集中在 `src/lib/`，改動範圍是 `db.ts` 的四個函式與各處 SQL 的方言差異 |
| 每月收款接近綠界個人會員上限 | 成立公司並申請特約商店（費率也會較低） |

在那之前，維持單機是對的：少一個元件就少一種故障。

## 發版流程

1. 開分支修改，`npm run check` 與 `npm run e2e` 通過。
2. 發 PR，CI 通過後合併到 main。
3. 部署（`fly deploy`）。資料表變更會在啟動時自動套用。
4. 開 `/api/health` 與首頁確認，五分鐘內留意日誌。
5. 有問題立刻回滾。資料表的變更只增不減，所以舊版程式仍可在新資料庫上運作。
